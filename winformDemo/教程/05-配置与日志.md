# 05 · 配置与日志

**目标**：能用 `appsettings.json` 改通道参数而不改代码，理解 Options 模式、启动校验、`ILogger<T>` 与「不吞异常」。

## 1. Options 模式

配置不是散落的 `JsonFileHelper.Load<T>()`，而是启动时一次性绑定成强类型对象：

```csharp
// Program.cs
builder.Services.Configure<AppOptions>(builder.Configuration.GetSection("App"));
```

```csharp
// 任何服务构造函数里
public CalibrationService(IOptions<AppOptions> options, ILogger<CalibrationService> logger)
{
    var cfg = options.Value;   // 已经反序列化好的 AppOptions
    ...
}
```

📌 好处：

- **类型安全**：`SampleIntervalMs` 是 `int`，不是字符串；写错字段名会在校验时被发现。
- **一处读取、处处注入**：不用每个页面各自去读文件。
- **可覆盖**：Generic Host 的配置提供程序按顺序叠加（JSON → 环境变量 → 命令行），所以 `App__SampleIntervalMs=200` 环境变量能覆盖 JSON，方便现场调试。
- **可校验**：`CalibrationService` 构造函数里主动检查通道数、量程合法性：

```csharp
if (cfg.Channels is null || cfg.Channels.Count != cfg.ChannelCount)
    throw new InvalidOperationException($"配置中的通道数 ... 不一致");

foreach (var (channel, index) in cfg.Channels.Select((c, i) => (c, i)))
    Validate(channel, index + 1);
```

📌 **Fail Fast（快速失败）**：参数非法时程序**启动时**就报错，而不是等采集时算出 `NaN`/`Infinity` 再显示一个错误的合格判定。对照旧项目 `yuzhiModel.jisuan()` 里 `0/0` 静默产生 `NaN`。

## 2. 路径：为什么固定 `ContentRootPath`

```csharp
var builder = Host.CreateApplicationBuilder(new HostApplicationBuilderSettings
{
    ContentRootPath = AppContext.BaseDirectory,
    Args = args
});
```

`AppContext.BaseDirectory` = 可执行文件所在目录（通常是 `bin/Debug/net8.0-windows/`），与配置复制目标、仓储输出目录一致。

旧项目有三个不同的路径基准：`JsonFileHelper` 用 `AppDomain.BaseDirectory`、`SqlHelper` 用相对路径 `data.db`、`Log` 用 `Directory.GetCurrentDirectory()`。用快捷方式或计划任务从别的工作目录启动时，数据库和日志会跑到别处，配置却还在 bin 里——非常难查。

📌 **规则**：桌面程序里凡是与程序自身相关的文件，一律基于 `AppContext.BaseDirectory` 拼绝对路径；`Directory.GetCurrentDirectory()` 只用于「用户当前选的工作目录」这类真正需要它的场景。

## 3. 日志：`ILogger<T>` 而不是 `Console.WriteLine`

```csharp
_logger.LogInformation("标定参数加载完成，共 {Count} 个通道", _channels.Count);
_logger.LogError(ex, "本周期采集失败，将在 {Interval} 后重试", _interval);
_logger.LogDebug("已持久化 {Count} 条记录", _items.Count);
```

📌 三个要点：

1. **结构化日志**：`{Count}` 是具名占位符（不是 `string.Format` 的 `{0}`），日志系统能按字段检索、聚合。
2. **分类**：`ILogger<CalibrationService>` 自动带类别名，可按命名空间过滤级别。
3. **级别**：Trace / Debug / Information / Warning / Error / Critical，生产环境可调，不用删代码。

最重要的是**异常不被吞掉**：

```csharp
catch (Exception ex)
{
    _logger.LogError(ex, "本周期采集失败，将在 {Interval} 后重试", _interval);
}
```

对照旧项目 `mainView.cs` 里那个空的 `catch (Exception ex) { }`——拔掉串口后界面静默不更新，没有任何线索。这里记录完整堆栈后继续下一周期，既不会让服务停摆，也不会"查无此事"。

📌 **日志实现可替换**：Generic Host 默认带 Console/Debug/EventSource 等 provider。生产环境加 Serilog/NLog 只需 `builder.Logging.AddSerilog(...)` 或在配置里加 sink，业务代码一行不改——又一个依赖倒置的例子。

## 🧪 动手实验

**实验 5.1 · 配置覆盖**
运行时用环境变量覆盖采样周期：

```bash
App__SampleIntervalMs=150 dotnet run
```

（Windows PowerShell：`$env:App__SampleIntervalMs=150; dotnet run`）。观察刷新变快，确认「环境变量优先于 JSON」。

**实验 5.2 · 调日志级别**
在 `appsettings.json` 根节点加：

```json
"Logging": {
  "LogLevel": {
    "Default": "Debug",
    "EnterpriseDemo": "Trace"
  }
}
```

重新运行，观察 `LogDebug("已持久化 ...")` 是否出现在输出窗口。再改回 `Information`，确认它消失。

**实验 5.3 · 启动校验**
把 `ChannelCount` 改成 `9` 但 `Channels` 仍保留 8 项，`dotnet run -- --self-test`。预期得到明确的「通道数不一致」异常。把 `ChannelCount` 改回 8。

**实验 5.4 · 加一个启动日志**
在 `Program.cs` 的 `host.Start()` 之前（需要先 `Build()` 才能拿 logger）加：

```csharp
host.Services.GetRequiredService<ILoggerFactory>()
    .CreateLogger("Startup")
    .LogInformation("应用启动，内容根目录：{Root}", AppContext.BaseDirectory);
```

运行，确认日志输出，并理解「组合根也能用日志」。

**实验 5.5 · 路径陷阱复现**
从另一个目录启动编译好的 exe：

```bash
cd /d D:\上位机
"D:\...\winformDemo\bin\Debug\net8.0-windows\WinformDemo.exe"
```

应该仍然正常读到 `appsettings.json`。把 `ContentRootPath` 那行临时删掉再试，观察差异（此时配置从当前工作目录找）。做完还原。

## 自测

1. `IOptions<T>` 与直接 `JsonConvert.DeserializeObject<T>` 比，多了什么？
2. 为什么把校验放在 `CalibrationService` 构造函数而不是每次 `Convert` 时？
3. `LogError(ex, "...")` 和 `LogError("..." + ex.Message)` 有什么区别？

<details><summary>答案要点</summary>

1. 集中绑定、多来源叠加与覆盖、按类别注入、生命周期由容器管理、便于测试（`Options.Create`）。
2. 参数启动后不变，校验一次即可；避免每 500 ms 重复判断，且能 Fail Fast。
3. 前者保留完整异常对象与堆栈，结构化日志系统能单独索引异常字段；后者只剩字符串，丢失堆栈与类型信息。

</details>
