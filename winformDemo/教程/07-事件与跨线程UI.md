# 07 · 事件与跨线程 UI

**目标**：彻底搞懂「后台线程为什么不能直接改控件」，以及本骨架为什么比 `Invoke` 更干净。

## 1. 规则从哪来

WinForms 控件与创建它的 **UI 线程**绑定。UI 线程跑消息循环，所有绘制、点击、输入都在这里排队执行。从线程池线程直接写 `textBox.Text` 会（默认开启检查时）抛：

```
InvalidOperationException: 线程间操作无效: 从不是创建控件"xxx"的线程访问它
```

更隐蔽的情况是检查被关掉：不报错，但出现随机重绘错误、数据错乱、偶发死锁。

## 2. 两种封送方式

**旧项目做法**（后台任务直接 `Invoke` 改控件）：

```csharp
// simpleView.cs（旧项目）
public void refreshData(double data, int i) {
    this.Invoke(new Action(() => {
        uiTextBox1.Text = data.ToString();
        uiLight1.OnColor = Color.Red;      // 业务判定混在 UI 代码里
        label3.Text = "不合格";
    }));
}
```

问题：业务服务必须知道控件存在；控件被销毁后 `Invoke` 抛异常被空 catch 吞掉；页面切走后后台还在刷。

**本骨架做法**（服务只发事件，表现层负责封送）：

```csharp
// Application/AcquisitionService.cs —— 没有任何 UI 类型
public event Action<IReadOnlyList<ChannelReading>>? BatchArrived;
...
BatchArrived?.Invoke(batch);       // 在采集线程上发布
```

```csharp
// Presentation/MainForm.cs
private readonly SynchronizationContext _uiContext;

public MainForm(...) {
    BuildUi();                     // 控件创建后，WinForms 已安装 UI 上下文
    _uiContext = SynchronizationContext.Current ?? new SynchronizationContext();
    _acquisition.BatchArrived += OnBatchArrived;
}

private void OnBatchArrived(IReadOnlyList<ChannelReading> batch) {
    _latest = batch.ToArray();
    _uiContext.Post(_ => RenderBatch(batch), null);   // 只做封送
}

private void RenderBatch(IReadOnlyList<ChannelReading> batch) {
    // 只在这里碰控件，且一定在 UI 线程
    ... 更新 BindingList ...
}
```

📌 `SynchronizationContext.Post` 把委托投递到创建上下文的线程消息队列；`Control.Invoke` 底层其实也是类似机制，但 `Post` 是**框架无关的抽象**，服务层不需要引用 `System.Windows.Forms`。WPF 版本会原样复用这段代码，只是上下文变成 `DispatcherSynchronizationContext`。

📌 `Post` 是异步（不等待）；`Send` 是同步（会等 UI 线程执行完，容易拖慢后台）。采集场景用 `Post` 合适。

## 3. 生命周期：别让后台服务持有死掉的页面

```csharp
protected override void OnFormClosed(FormClosedEventArgs e) {
    _acquisition.BatchArrived -= OnBatchArrived;   // 取消订阅
    base.OnFormClosed(e);
}
```

事件是强引用：`AcquisitionService`（单例，活得比窗口久）订阅列表里若还留着 `MainForm`，窗口就无法被回收 → 内存泄漏 + 向已销毁控件 `Post`。**谁订阅，谁负责取消订阅**，这是 .NET 事件最容易忽略的一条纪律。WPF 版在 `MainWindow.Closed` 里调 `MainViewModel.Unsubscribe()`，思路一致。

## 4. 数据竞争怎么消失的

旧项目用 `static double[] data` 让后台写、UI 读，没有任何同步。本骨架：

- 每批数据打包成 `IReadOnlyList<ChannelReading>`，`ChannelReading` 是**不可变 record**；
- `OnBatchArrived` 里先 `_latest = batch.ToArray()` 做快照（同一个采集线程写，保存按钮在 UI 线程读——严格说这里仍有极小的可见性竞态，但读的是引用快照，不会出现"半个数组"；生产环境可用 `Volatile.Read/Write` 或 `ImmutableArray`）；
- 判定结果（`IsQualified`）在**服务层**算好，UI 只显示 `合格/不合格` 字符串，不再自己比较阈值。

📌 **判定属于业务，不属于 UI**：旧项目把 `Convert.ToDouble(阈值)` 和比较放在 `simpleView.refreshData` 里，导致 UI 代码必须知道标定参数。这里 UI 只拿到结果。

## 🧪 动手实验

**实验 7.1 · 抓一次跨线程异常（强烈建议做）**
把 `OnBatchArrived` 里的 `_uiContext.Post(...)` 临时改成直接 `RenderBatch(batch)`，运行。预期：抛「线程间操作无效」，或在输出窗口看到异常。做完还原。这个实验比读十段解释都管用。

**实验 7.2 · 确认线程 ID**
在 `OnBatchArrived` 和 `RenderBatch` 里各加一行：

```csharp
Console.WriteLine($"thread={Environment.CurrentManagedThreadId}");
```

不过 WinExe 没有控制台，改用 `_logger.LogInformation("thread={Id}", Environment.CurrentManagedThreadId)` 并在 VS 输出窗口看，或写到一个临时文件。预期：两个 ID 不同。

**实验 7.3 · 观察取消订阅的效果**
注释掉 `OnFormClosed` 里的 `-=`，运行，在 `RenderBatch` 里打日志；关闭窗口后 Host 会很快停止（采集停了，看不出泄漏）。为了看清问题，把 `SampleIntervalMs` 调大、并在 `OnExit` 里延迟 `StopAsync`，观察是否还有向已关闭窗口的 Post。**重点是养成写 `-=` 的习惯。**

**实验 7.4 · 用 `Progress<T>` 重写（进阶）**
.NET 提供 `Progress<T>`：在 UI 线程构造 `var progress = new Progress<IReadOnlyList<ChannelReading>>(RenderBatch);`，把它交给服务，服务调 `IProgress<T>.Report(batch)` 即自动封送。试着重构一遍，对比两种写法的可读性。这也是很多企业级项目采用的方案。

## 自测

1. `SynchronizationContext.Post` 和 `Control.Invoke` 的核心区别是什么？
2. 为什么要在**控件创建之后**才捕获 `SynchronizationContext.Current`？
3. 判定逻辑放在 UI 层有什么坏处？

<details><summary>答案要点</summary>

1. `Post` 是框架无关的抽象、异步投递，不需要控件引用；`Invoke` 必须持有控件、同步等待。前者让服务层完全不依赖 WinForms。
2. WinForms 在创建第一个控件时才安装 `WindowsFormsSynchronizationContext`；在此之前 `Current` 可能是普通上下文或 null。
3. UI 必须知道阈值配置，业务规则分散；换 UI 框架要重写；无法单独测试判定逻辑；跨线程读配置又有竞态。

</details>
