# 04 · 接口与依赖倒置

**目标**：能新增一个实现类，并且**只改组合根一行**就让整个应用换掉硬件或数据库。

## 1. 三个接口，三种「可替换点」

打开 `Core/Abstractions.cs`：

```csharp
public interface IModbusClient : IDisposable
{
    bool IsConnected { get; }
    Task ConnectAsync(CancellationToken cancellationToken);
    Task<ushort[]> ReadChannelsAsync(CancellationToken cancellationToken);
}

public interface ICalibrationService
{
    int ChannelCount { get; }
    double Convert(int channel, ushort raw);
    (double Low, double High) LimitsOf(int channel);
}

public interface IMeasurementRepository
{
    Task AddAsync(SampleRecord record, CancellationToken cancellationToken = default);
    Task<IReadOnlyList<SampleRecord>> QueryAsync(
        DateTime? from, DateTime? to, string? project,
        CancellationToken cancellationToken = default);
}
```

| 接口 | 隔离了什么 | 将来换成 |
|---|---|---|
| `IModbusClient` | 物理设备与通信协议 | 基于 NModbus 的真实 `NModbusClient`、TCP Modbus、OPC UA |
| `ICalibrationService` | 标定算法 | 多点最小二乘标定、带温度补偿的标定 |
| `IMeasurementRepository` | 持久化方式 | SQLite / EF Core / SQL Server / 云端 API |

📌 **接口放在 Core，实现放在 Infrastructure**：这是依赖倒置的关键。传统三层里「业务层引用数据层」；这里业务层只引用 Core 里的抽象，数据层反过来"实现"业务层定义的契约。

## 2. 依赖倒置（DIP）与开闭原则（OCP）

- **DIP**：高层模块（`AcquisitionService`）不依赖低层模块（`SimulatedModbusClient`），二者都依赖抽象（`IModbusClient`）。
- **OCP**：要换设备时，对**扩展**开放（新增一个类），对**修改**关闭（`AcquisitionService`、`MainForm` 一行都不改）。

对照旧项目：主流程写死 `mainCommon.modbusRtu.ReadHoldingRegisters(0, 8)`，想接 Modbus TCP 就得改 `mainView`、`mainCommon`，还要重新测界面。

## 3. 接口设计里的几个讲究

**a) 只暴露抽象需要的最小面**：`IModbusClient` 没有 `PortName`、`BaudRate`、`SlaveId` 这些具体设备属性——连接参数属于实现类的配置，不该泄漏给业务层。

**b) 异步 + 取消令牌**：真实串口读取会阻塞，所以接口直接是 `Task` + `CancellationToken`，避免将来从同步改成异步时波及所有调用方。

**c) 继承 `IDisposable`**：设备占用非托管资源（串口句柄），容器在关闭时会 dispose 单例。

**d) 返回只读集合**：`IReadOnlyList<SampleRecord>` 表示「调用方别改我的内部列表」。

**e) `record` 不可变**：`ChannelReading` / `SampleRecord` 是 `record`，属性只有 `init`/位置参数，跨线程传递不会被谁偷偷改掉——这正是旧项目 `static double[] data` 做不到的。

## 🧪 动手实验

### 实验 4.1 · 换一个「固定值」设备（核心实验）

在 `Infrastructure/` 新建 `ConstantModbusClient.cs`：

```csharp
using EnterpriseDemo.Core;

namespace EnterpriseDemo.Infrastructure;

public sealed class ConstantModbusClient : IModbusClient
{
    private bool _connected;
    public bool IsConnected => _connected;

    public Task ConnectAsync(CancellationToken ct)
    {
        _connected = true;
        return Task.CompletedTask;
    }

    public Task<ushort[]> ReadChannelsAsync(CancellationToken ct)
    {
        // 所有通道固定返回 2800，方便验证标定与判定
        return Task.FromResult(Enumerable.Repeat((ushort)2800, 8).ToArray());
    }

    public void Dispose() => _connected = false;
}
```

然后**只改组合根一行**：

```csharp
builder.Services.AddSingleton<IModbusClient, ConstantModbusClient>();
```

运行 `dotnet run -- --self-test` 和 `dotnet run`。预期：所有通道原始值恒为 2800，通道1 工程值恒为 `26.00 mm`，判定恒为「合格」（因为 `26` 落在 `[26, 28]` 且用 `>=`/`<=`）。

✅ **验收标准**：`AcquisitionService.cs`、`MainForm.cs`、`Core/` 里一个字都没改。改回来再继续。

### 实验 4.2 · 换一个内存仓储

新建 `InMemoryMeasurementRepository.cs`，实现 `IMeasurementRepository`，内部用 `List<SampleRecord>`，不写文件。改一行注册，运行，点保存，确认历史表格能更新；重启程序后历史为空（因为没落盘）。这个实验让你直观感到「持久化策略」是一个可以插拔的部件。

### 实验 4.3 · 写第一个单元测试（不需要窗口）

新建一个控制台/xUnit 项目（或直接写在自检分支里），只做：

```csharp
var cfg = new ChannelConfig { RawLow = 2200, RawHigh = 3200,
                             ValueLow = 20, ValueHigh = 30,
                             LimitLow = 26, LimitHigh = 28 };
// 断言：2200->20, 2700->25, 3200->30
```

因为标定类只依赖 `IOptions<AppOptions>` 和 `ILogger`，你可以用 `Options.Create(new AppOptions { ... })` 和 `NullLogger<CalibrationService>.Instance` 直接构造，**不需要启动窗口、不需要串口**。这就是可测试性。

### 实验 4.4 · 验证接口隔离

在 `AcquisitionService.cs` 里搜索 `Simulated`、`Json`、`CalibrationService`（具体类名）。应该一个都没有，只有接口名。如果出现了具体类名，说明依赖倒置被破坏。

## 自测

1. 为什么 `IModbusClient` 定义在 `Core` 而不是 `Infrastructure`？
2. 接口方法为什么带 `CancellationToken`？
3. 「换设备只改一行」这一行改的是什么？为什么其它层不用改？

<details><summary>答案要点</summary>

1. 让业务层依赖自己定义的抽象，实现层反过来依赖 Core；若放在 Infrastructure，Application 就必须引用 Infrastructure，依赖方向反转、无法替换。
2. 真实 IO 可取消、可超时；接口从一开始就异步，将来换实现不必改调用方，也让 Host 关闭时能立刻中断读取。
3. 组合根里 `AddSingleton<IModbusClient, Xxx>()` 的映射；因为所有调用方只持有接口引用，容器负责把新实现注入进去。

</details>
