# 09 · 表现层与数据绑定

**目标**：读懂 `MainForm.cs`，理解「表现层薄到什么程度才算合格」，以及 `BindingList` 为什么能自动刷新表格。

## 1. 这个类做了什么、没做什么

打开 `Presentation/MainForm.cs`，按职责分成四块：

| 代码块 | 职责 |
|---|---|
| 字段 + 构造函数 | 接收注入的三个依赖、构建界面、捕获 UI 上下文、订阅事件 |
| `BuildUi()` / `CreateGrid<T>()` | 纯布局，创建控件 |
| `OnBatchArrived()` / `RenderBatch()` | 线程封送 + 把 `ChannelReading` 映射成表格行 |
| `OnSaveClick()` / `LoadHistoryAsync()` | 把用户动作翻译成仓储调用 |
| `OnFormClosed()` | 取消订阅 |

**没有的**：标定公式、串口、文件路径、SQL、JSON、线程创建、后台循环。整个类只有「显示」和「转发」。

📌 判断表现层是否够薄的方法：把 `MainForm` 整个删掉，换成控制台输出，`Application`/`Infrastructure` 层能不能原样工作？本骨架可以（自检模式已经证明了一半）。

## 2. 为什么用代码构建 UI，而不是 Designer

真实企业级 WinForms 项目通常使用 `.Designer.cs` 做复杂界面（可视化、易维护、支持本地化）。本骨架刻意用 `BuildUi()` 纯代码构建，原因：

- **文件数少**：9 个 `.cs` 就能跑起来，不产生 6 个几百行的 Designer 文件淹没重点；
- **一眼看全**：布局、绑定、事件都在一个文件里，适合学习；
- **便于对照 WPF**：`BuildUi()` 与 `MainWindow.xaml` 的结构可以逐行比对。

⚠️ 这是**教学取舍**，不是"企业里不该用 Designer"。第 10 章会给出把 UI 拆成 UserControl + Designer 的路线。

## 3. `BindingList` 与数据绑定

```csharp
private readonly BindingList<ChannelRow> _liveRows = new();
private readonly BindingList<SampleRow> _historyRows = new();

uiDataGridView.DataSource = _liveRows;     // CreateGrid<T> 里设置
```

`BindingList<T>` 实现 `IBindingList`，在增减元素时发 `ListChanged`，`DataGridView` 收到后自动增删行。列由 `AutoGenerateColumns = true` 根据行对象的 public 属性生成，列名取自 `[DisplayName]`：

```csharp
public sealed class ChannelRow
{
    [DisplayName("通道")] public int Channel { get; set; }
    [DisplayName("原始值")] public ushort Raw { get; set; }
    [DisplayName("工程值 / mm")] public double Value { get; set; }
    [DisplayName("判定")] public string Result { get; set; } = "";
}
```

📌 **修改已有行的属性不会自动刷新**（对象本身没实现 `INotifyPropertyChanged`），所以 `RenderBatch` 末尾调：

```csharp
_liveRows.ResetBindings();     // 通知「整表重读」
```

8 行数据这样完全够用；数据量大时应让行实现 `INotifyPropertyChanged`，或改用虚拟模式。

📌 `ChannelRow` / `SampleRow` 是**表现层自己的行模型（View Model 的雏形）**，不是领域模型 `ChannelReading`。好处：界面想显示「合格」而不是 `True`、想把数值四舍五入到 3 位，都在表现层完成，不污染领域模型。

## 4. 异步事件处理

```csharp
private async void OnSaveClick(object? sender, EventArgs e)
{
    try {
        var record = new SampleRecord(...);
        await _repository.AddAsync(record);
        await LoadHistoryAsync();
        _status.Text = $"已保存 {record.Time:HH:mm:ss}";
    } catch (Exception ex) {
        _logger.LogError(ex, "保存检测记录失败");
        _status.Text = "保存失败：" + ex.Message;
    }
}
```

📌 `async void` 在 WinForms 事件里是**唯一可接受**的常见场景（事件委托签名要求 `void`），但必须包住整个方法体的 `try/catch`，否则异常会跑到消息循环里变成未处理异常。企业级代码通常封装成 `AsyncRelayCommand` 或 `ICommand`（WPF 版就是这么做的，第 04 章会对照）。

📌 `await` 之后默认**回到 UI 线程**（因为捕获了 `SynchronizationContext`），所以 `await` 后面直接改 `_status`、`_historyRows` 是安全的，无需再 `Invoke`。

## 5. 与旧项目的对照

| 旧项目 | 本骨架 |
|---|---|
| `mainView.cs` 里同时做采集、标定、判定、保存、隐藏通道 | `MainForm` 只显示与转发 |
| `simpleView.refreshData` 在 `Invoke` 里做阈值比较与灯颜色 | 判定在 `AcquisitionService`，UI 只显示字符串 |
| `BindingList<dataModel>` 直接绑数据库模型 | `ChannelRow`/`SampleRow` 独立行模型 |
| `uiDataGridView1.Columns[i]` 隐藏列索引错位 | 表格列由行模型自动生成，无魔法下标 |
| 页面被 `Controls.Clear()` 移除后仍被后台 `Invoke` | `OnFormClosed` 取消订阅 |

## 🧪 动手实验

**实验 9.1 · 让行实现属性通知**
给 `ChannelRow` 实现 `INotifyPropertyChanged`（或用 `ObservableObject`），在属性 setter 里触发事件，然后删掉 `_liveRows.ResetBindings()`。运行，确认表格仍然实时刷新。体会两种刷新粒度的差异。

**实验 9.2 · 加一列「时间戳」**
在 `ChannelRow` 加 `[DisplayName("时间")] public string Time { get; set; }`，在 `RenderBatch` 里填 `reading.Timestamp.ToString("HH:mm:ss.fff")`。运行确认自动多出一列——这就是 `AutoGenerateColumns` + `DisplayName` 的便利。

**实验 9.3 · 显示成中文布尔值以外的形式**
把 `Result` 改成 `合格 ✔ / 不合格 ✘`，或加一个 `Color` 字段并用 `CellFormatting` 事件染色。注意：**所有美化都只改 `MainForm`**，其它层不用动。

**实验 9.4 · 验证表现层可替换**
把 `RenderBatch` 里的 `_liveRows.ResetBindings()` 注释掉，改成把数据写到一个 `ListBox`。运行，确认整个应用仍然工作。然后还原。

## 自测

1. `BindingList` 和 `List` 在数据绑定上的区别是什么？
2. `await` 之后为什么可以直接改控件？
3. `async void` 有什么风险？本骨架怎么规避？

<details><summary>答案要点</summary>

1. `BindingList` 实现 `IBindingList` 并在增删时发 `ListChanged`，`List` 不会，绑定后需手动 `ResetBindings()`。
2. `await` 捕获了 UI 线程的 `SynchronizationContext`，continuation 默认回到该线程。
3. 异常无法被调用方 await 捕获，会变成未处理异常；因此方法体必须整体 `try/catch`，并配合日志。

</details>
