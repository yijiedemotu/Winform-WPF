# 01 · 先跑起来

**目标**：编译、自检、运行 WPF 窗口，并确认「数据链路和第一套一模一样，只有最后一公里不同」。

## 1. 编译与自检

```bash
cd wpfDemo
dotnet build
dotnet run -- --self-test
```

`--self-test` 在 `App.xaml.cs` 的 `OnStartup` 里：

```csharp
if (e.Args.Contains("--self-test"))
{
    var calibration = _host.Services.GetRequiredService<ICalibrationService>();
    var repository  = _host.Services.GetRequiredService<IMeasurementRepository>();
    File.WriteAllText(..., $"OK | channels={calibration.ChannelCount} | ...");
    _host.Dispose();
    _host = null;
    Shutdown();          // 不创建任何 Window
    return;
}
```

📌 与 WinForms 版的差别只是「怎么退出」：那边 `return` 就结束 `Main`；WPF 由 `Application` 托管消息循环，必须显式 `Shutdown()`。**这份差异只存在于组合根里**。

预期输出同样是 `OK | channels=8 | repo=JsonMeasurementRepository | 通道1 raw=2700 -> 25.00 mm`。

若编译报错 `Path`/`File` 不存在：检查 csproj 里的 `<Using Include="System.IO" />`。WPF SDK 的隐式 using 集合比 WinForms 少 `System.IO`，骨架在项目层补齐，目的是让业务层源码保持逐字节一致——这本身就是一次「差异应该由谁吸收」的教学示范。

## 2. 打开窗口

```bash
dotnet run
```

界面和第一套功能一致：上面 8 行实时通道数据，下面历史记录，顶部产品名 + 两个按钮 + 状态文字。每 500 ms 刷新。

数据链路（对照第一套第 01 章）：

| 步骤 | 文件 | 与第一套 |
|---|---|---|
| 1. 模拟设备产生 `ushort[8]` | `Infrastructure/SimulatedModbusClient.cs` | 完全相同 |
| 2. 定时读取 | `Application/AcquisitionService.cs` | 完全相同 |
| 3. 标定 / 判定 | `Infrastructure/CalibrationService.cs` | 完全相同 |
| 4. 打包 `ChannelReading` | `Core/Models.cs` | 完全相同 |
| 5. 发布 `BatchArrived` | `AcquisitionService` | 完全相同 |
| 6. 封送回 UI 线程 | `ViewModels/MainViewModel.cs` → `OnBatchArrived` | **实现不同，机制相同** |
| 7. 更新集合、绑定刷新 | `MainViewModel.Render` → `ObservableCollection` | **不同** |

```csharp
// 第一套 MainForm.cs
_uiContext.Post(_ => RenderBatch(batch), null);
// 第二套 MainViewModel.cs
_uiContext.Post(_ => Render(batch), null);
```

**一模一样的一行代码**。区别只在 `SynchronizationContext.Current` 的具体类型：WinForms 是 `WindowsFormsSynchronizationContext`，WPF 是 `DispatcherSynchronizationContext`。第 09 章会展开。

## 3. 谁把 ViewModel 和 View 连起来

```csharp
// Views/MainWindow.xaml.cs
public MainWindow(MainViewModel viewModel)
{
    InitializeComponent();
    _viewModel = viewModel;
    DataContext = viewModel;             // 一句话建立绑定源
    Closed += (_, _) => _viewModel.Unsubscribe();
}
```

XAML 里的 `{Binding ProjectName}`、`{Binding SaveCommand}`、`{Binding Channels}` 全部从 `DataContext` 取值。**DataContext 是 MVVM 的接线柱**，也是 code-behind 唯一必须做的事（外加生命周期转发）。

## 🧪 动手实验

**实验 1.1 · 确认业务层零改动**
按 `00-学习路线` 里的 7 条 `diff` 命令跑一遍，全部应无输出。用 `fc /b` 或 `Compare-Object` 也可以。

**实验 1.2 · 改采样周期**
把 `appsettings.json` 的 `SampleIntervalMs` 改成 `150`，运行，观察刷新变快。注意：你改的是**共享配置**，两套都会受影响——这正是「配置与代码分离」的效果。改回 500。

**实验 1.3 · 让 DataContext 失效**
把 `DataContext = viewModel;` 临时注释掉，运行。预期：界面空白、状态文字不显示、按钮点了没反应，但**后台采集仍在跑**（输出窗口有日志）。这能让你直观看到「View 与 ViewModel 只是通过 DataContext 松耦合连接」。做完还原。

**实验 1.4 · 保存并落盘**
点几次「保存数据」，打开 `bin/Debug/net8.0-windows/samples.json`，确认与第一套生成的数据结构一致。甚至可以：先用 WinForms 版保存几条，再用 WPF 版打开，看到同样的历史记录——**两个程序共用同一份仓储实现与数据格式**。

## 自测

1. WPF 的 `--self-test` 为什么要显式 `Shutdown()`？
2. `DataContext` 起什么作用？删掉之后后台服务会停吗？
3. 两套程序的数据链路在哪一步开始分叉？

<details><summary>答案要点</summary>

1. WPF 由 `Application` 托管消息循环，`OnStartup` 返回后不会自动结束进程。
2. 它是所有 `{Binding}` 的默认源；删掉只是视图拿不到数据，DI 容器与后台服务照常运行。
3. 第 6 步（封送后的呈现方式）：之前 1~5 完全相同，第 6 步代码甚至一样，只是上下文类型不同；真正的差异在 View/ViewModel 如何把数据画出来。

</details>
